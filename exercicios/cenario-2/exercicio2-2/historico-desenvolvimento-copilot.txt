Arquivos implementados
src/shared/logger.ts — singleton pino com nível info em produção e debug nos demais ambientes, campo fixo service: "novatech-assistant".

src/functions/query/validator.ts — QueryInputSchema (Zod) com question: string, min 3, max 500 + tipo inferido QueryInput. Mensagens de erro em inglês e descritivas.

src/functions/query/handler.ts — Azure Functions v4, rota POST /api/query. Fluxo:

Parse JSON falha → 400 { error: "validation_error" }
Zod falha → 400 { error: "validation_error", detail: "<mensagens>" }
Sucesso → 200 { status: "ok", question } (placeholder para QE-009)
Logging via pino.child({ requestId }) para correlação de logs
src/functions/query/response-builder.ts — QueryOutputSchema (Zod) com answer e source_documents[] + buildResponse() que deduplica e ordena as fontes.

Revisão crítica (Tarefa 3 do exercício)
Dois pontos que precisariam de ajuste antes de um code review real:

authLevel: 'anonymous' — o handler está sem autenticação. Em produção, deveria ser 'function' com chave de API ou usar o API Gateway da NovaTech como proxy autenticador. Deixar anônimo expõe o endpoint publicamente.

Ausência de validação de output — o response-builder.ts usa QueryOutputSchema.parse() que lança uma exceção genérica (ZodError) não tratada pelo handler. O QE-009 precisará capturar isso separadamente — um answer vazio retornado pelo LLM quebraria silenciosamente em produção sem um ResponseBuildError tipado e um 500 adequado.
