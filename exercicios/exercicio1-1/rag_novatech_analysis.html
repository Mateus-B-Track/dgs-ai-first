Desafio
Tabelas com 15+ colunas extraídas como texto linear perdem a estrutura dimensional. Um chunk que contém "destino, peso 1–5kg, peso 6–10kg, zona norte, zona sul…" sem cabeçalhos é semanticamente opaco para o retriever e para o LLM. Fluxogramas embutidos como imagens são ignorados completamente pela maioria dos parsers de texto.
Impacto
O assistente responderá perguntas como "qual o frete para 8kg, destino Sul?" com dados incorretos ou recusará a resposta por falta de contexto estruturado. A taxa de erro em perguntas numéricas pode ultrapassar 40% com chunking ingênuo.
Estratégia
Azure Document IntelligenceTable serializationMarkdown table format
Usar Azure Document Intelligence (Layout model) para extração estruturada. Serializar cada tabela como Markdown ou JSON com cabeçalhos repetidos por linha. Cada linha da tabela = 1 chunk autossuficiente, ex.: "Tabela de frete | Peso: 6–10kg | Destino: Sul | Prazo SLA: 3 dias úteis | Valor: R$ 45,00". Para fluxogramas, gerar descrição textual via GPT-4o Vision como metadado enriquecido.
Desafio
Documentos escaneados produzem texto com taxa de erro de caractere (CER) de 2–8% em OCR padrão, chegando a 15–25% em PDFs de baixa qualidade (< 150 DPI). Erros como "prazo de 3 dias üteis" ou "R$4S,00" são invisíveis para o pipeline mas fatais para precisão das respostas.
Impacto
Além de erros numéricos, metadados estruturais (datas de vigência dos documentos, números de versão) ficam ilegíveis, impossibilitando filtros temporais. Um documento de política desatualizado pode ser recuperado e citado como fonte vigente.
Estratégia
Azure AI Vision OCRConfidence scoringHuman-in-loop para CER > 5%
Pipeline em dois estágios: (1) Azure AI Vision OCR com confidence score por token — chunks com score médio < 0,85 entram em fila de revisão humana antes de indexação. (2) Pré-processamento com modelos de linguagem para post-OCR correction em passagens numéricas. Obrigatório metadado de "confiança do OCR" e "data do documento" em cada chunk para filtros de retrieval.
Desafio
Links internos entre páginas criam dependências de contexto: a Página A define "Nível 1 de cliente", a Página B usa o termo sem defini-lo. Um chunk de B sem o contexto de A produzirá resposta incompleta. Macros customizadas (tabelas de status, painel de tarefas, expanders) são exportadas como HTML não interpretado ou simplesmente omitidas.
Impacto
Termos técnicos internos da NovaTech (siglas de área, códigos de SLA, tipos de cliente) ficarão sem definição no contexto, causando respostas genéricas ou confusas. Estimamos que ~30% das páginas do Confluence da NovaTech dependem de contexto de outra página.
Estratégia
Confluence API v2Graph-aware chunkingGlossário centralizado
Usar Confluence REST API v2 para exportação com resolução de links (incluir título + primeiro parágrafo da página vinculada como metadado contextual do chunk). Construir um grafo de dependência entre páginas para identificar "páginas âncora" que devem ser recuperadas em conjunto. Macros: parsear o HTML exportado e converter painel de status em texto estruturado, ignorar macros puramente visuais.
Desafio
Fórmulas como =VLOOKUP(A2,TabelaClientes,3,FALSE) são texto sem semântica para o LLM. O valor computado depende de células em outras abas (e potencialmente outros arquivos), tornando os dados estáticos na exportação. Planilhas atualizadas mensalmente criam risco de desatualização se o pipeline de ingestão não for automatizado.
Impacto
Se a planilha de SLA for indexada com valores calculados em uma data e o atendente consultar 3 semanas depois (pós-atualização mensal), as respostas estarão desatualizadas. Planilhas com múltiplas abas interdependentes podem produzir chunks contraditórios entre si.
Estratégia
Exportação de valores calculadosTrigger automático mensalDesnormalização estruturada
Nunca indexar fórmulas, apenas valores calculados exportados via openpyxl com evaluate=True. Desnormalizar as abas em tabelas planas antes do chunking — cada linha deve ser autossuficiente com todas as colunas relevantes. Configurar trigger de re-ingestão automática no SharePoint (Power Automate) para qualquer arquivo .xlsx modificado, com versionamento de chunks por hash do conteúdo para detectar mudanças reais vs. salvamentos sem alteração.

Perguntas multi-domínio (ex: SLA + frete simultâneos): Uma pergunta como "qual o prazo para cliente Nível 2 com carga de 12kg para o Norte?" exige chunks de pelo menos 3 fontes diferentes (tabela de SLA, tabela de frete, definição de nível de cliente). Com chunks de 500 tokens cada, precisamos de no mínimo 6–9 chunks de qualidade para cobrir todos os domínios — e o retriever por similaridade semelhante tipicamente não recupera bem múltiplos domínios em uma única query. Solução: query decomposition (quebrar a pergunta em sub-queries) + multi-step retrieval antes da geração.

4
Recomendação de estratégia de chunking

A NovaTech tem dois perfis de pergunta dominantes, com necessidades de chunking opostas:

Tipo A — Perguntas diretas
Chunks pequenos (200–350 tokens)
"Qual o prazo para cliente Padrão?" — a resposta está em 1–2 linhas de uma tabela. Chunks grandes diluem o sinal semântico e o retriever recupera chunks irrelevantes.
Tipo B — Perguntas contextuais
Chunks médios (400–600 tokens)
"Como funciona o processo de reclamação para avaria de carga?" — exige contexto de procedimento multi-etapa. Chunks pequenos fragmentam o raciocínio necessário.
Por que chunking fixo sem overlap é problemático aqui: Com documentos de procedimento multi-etapa, um chunk pode terminar no meio de uma instrução: "…acione o operador responsável. Em seguida, [CORTE DE CHUNK] preencha o formulário F-07 com…". O segundo chunk não tem contexto suficiente para ser recuperado na query original. Estimamos que ~15–20% das informações críticas da NovaTech estejam em posições de fronteira de chunk com chunking fixo de 500 tokens.

Estratégia recomendada: chunking hierárquico com overlap adaptativo

  • 1
    Segmentação semântica primária — usar estrutura natural do documento (títulos H1/H2, seções, breaks de tabela) como fronteiras de chunk, não tamanho fixo em tokens. Isso preserva unidades de significado completas.
  • 2
    Overlap de 10–15% entre chunks adjacentes — ~50–70 tokens de sobreposição. Para chunks de 500 tokens, isso significa repetir as últimas 2–3 frases no início do próximo chunk. Custo: +15% de espaço de índice. Benefício: elimina o problema de fronteira de chunk estimado em ~15–20% das perdas de informação.
  • 3
    Chunks pai–filho (parent-child chunking) — indexar chunks pequenos (200 tokens) para recuperação precisa, mas retornar o chunk pai (500–800 tokens) ao LLM para geração. Isso combina alta precisão de retrieval com contexto suficiente para geração de qualidade.
  • 4
    Metadados obrigatórios em cada chunk — fonte (SharePoint/Confluence/Excel), nome do documento, data de última atualização, área responsável (Operações/Compliance/Comercial), nível de confiança OCR (quando aplicável). Esses metadados permitem filtros de retrieval que aumentam precisão sem aumentar o número de chunks no contexto.
  • 5
    Tratamento especial para documentos contraditórios — dado que a NovaTech tem documentos em versões conflitantes, adicionar metadado de versão + data e configurar o prompt para priorizar a versão mais recente explicitamente quando houver múltiplos chunks do mesmo tópico com datas diferentes.
Impacto esperado na meta de negócio: com retrieval em < 2s (vs. busca manual atual de 12 min) e acurácia de resposta > 85% (meta conservadora com a estratégia acima), a redução de tempo por chamado alcança facilmente o objetivo de < 2 minutos. O principal risco residual é a qualidade da ingestão das tabelas de frete — o ponto de maior complexidade técnica do projeto.
